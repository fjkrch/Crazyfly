# Training and checkpoints

`scripts/train.py` performs an explicit small recurrent-PPO pilot. It saves model, optimizer, Torch RNG, seed, task, policy dimensions, PPO configuration, circuit checksum, core checksum, and metric history in `runs/<UTC>/<task>/<policy>/seed-<n>/`. The actor observations use fixed task-level scaling, so no running normalizer is needed in the current task version.

The smoke default is 16 environments, 32 control steps per rollout, and 10 updates. It is a functional/update gate, not an efficacy result. Before comparison runs, establish a separately declared learning pilot; do not fabricate a success rate when that gate fails.

The collector continues simulator observations and per-environment recurrent state across PPO update boundaries. It saves the state at each sequence start for log-probability replay, and only masks environments that actually reset. Truncated BPTT uses that stored boundary state as a constant; because the encoder may have changed since the preceding rollout, this is a documented stale-state approximation. CPU continuation/replay tests and short simulator pilots have executed. The first full-budget original-LIF attempt stopped after roughly 16 PPO updates, before checkpoint, on a stored/replayed policy log-probability mismatch before an update. The current 256-neuron backend has since passed a 60-update replay run through the 1,000-step reset boundary; that narrower proof does not establish five-million-interaction stability or useful learning.

Isaac Lab returns post-reset observations after done. The project launcher captures policy observations immediately before its internal reset and the PPO runner uses those observations for time-limit value bootstrapping. The stored checkpoint supports functional fresh-process reload, not exact continuation of a mid-episode simulator state.

The command emits JSON with saved queue counts, matching live runner/child PIDs, the latest completed PPO update and expected update count, active-stage log age, and observed checkpoint/evaluation files. `needs_inspection` flags stale output or absent processes for investigation; it is a single read-only observation, not a terminal verdict. File existence alone does not validate a checkpoint or evaluation result; the matrix runner and summarizer perform those checks.

For a new queue, `scripts/run_matrix.py --dry_run` starts nothing and `--queue_only` checks prerequisites and marks untouched eligible jobs ready without starting them or resetting valid partial job states. Execution requires the smoke report to match the current task and diagnostic source fingerprint, include bounded random actions at scale 0.1–1.0, and record at least 16 environments × 1,000 steps. The real MaleCNS manifest is available at the path above. The queue runs jobs sequentially, saves training and evaluation logs, and revalidates checkpoint metadata and evaluation records before skipping completed work on resume. An exclusive queue lock prevents concurrent runners; a child silent for five minutes is stopped and marked failed, while active jobs have no total-time limit.

With a full-budget checkpoint and its matching 16-episode held-out JSON now available, [`record_heldout_regimes.py`](../scripts/record_heldout_regimes.py) can run a deterministic companion replay in a separate Isaac process and save bounded pre-action root-pose and named contact-sensor traces. It verifies the checkpoint, schedule, paired plans, and initial states, then compares success, target times, scheduled events, and total control steps with the reference evaluation. Matching these does not prove byte-identical trajectories. [`regime_metrics.py`](../scripts/regime_metrics.py) computes CPU-only root-height/orientation and per-body net-force summaries by episode and training seed. The analyzer requires a declared force threshold: the planned primary comparison uses 20 N with root-axis cosine 0.5, with 10 N and 50 N sensitivity checks. These are observable proxies, not proof of ground support, walking, or crawling. [`execute_regime_matrix.sh`](../scripts/execute_regime_matrix.sh) will run all 60 companion recordings sequentially and write validated JSON/Markdown comparisons once the main matrix is complete. Do not start those replays until the resumed main queue completes with 20/20 validated jobs; no 16-environment companion simulator replay has run yet on a full-budget checkpoint.
